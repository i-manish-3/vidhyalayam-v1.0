# Admission Module Flow

This document explains how the admission module works from the frontend wizard to API logic and database storage.

## 1. Entry Point

The admission form is opened from the sidebar menu:

`src/components/app-sidebar.tsx`

```ts
{ label: 'Add New Admission', page: 'admission-form', icon: UserPlus }
```

The project uses Zustand navigation state instead of a dedicated URL route for this page. When `currentPage` becomes `admission-form`, `src/components/app-layout.tsx` dynamically loads:

```ts
@/features/admissions/pages/admission-form-page
```

## 2. Frontend Wizard

The main admission form component is:

`src/features/admissions/pages/admission-form-page.tsx`

It is a 6-step wizard:

1. Personal Details
2. Contact Info
3. General Details
4. Accounts Info
5. Documents
6. Review & Submit

The form data is stored in local React state:

```ts
const [form, setForm] = useState<WizardForm>({ ...DEFAULT_FORM })
```

The component also tracks:

- `currentStep`
- `completedSteps`
- `fieldErrors`
- `touched`
- `documentUploads`
- `siblingResults`
- `selectedSibling`

## 3. Initial Data Fetching

When the admission form loads, it fetches the minimal set of dropdown and helper data that does **not** depend on the chosen academic year:

```ts
/api/school/sections
/api/school/admissions/next-number
/api/school/academic-years
```

Classes, fees groups, and transport routes are fetched **reactively** based on subsequent user selections — see Section 3a.

This initial data is used for:

- section selection (filtered client-side by chosen class)
- admission number preview
- academic year dropdown options

## 3a. Reactive Dropdowns — Academic Year → Class → Fees Group

The admission form follows a strict hierarchy: a class cannot be picked until an academic year is chosen, and a fees group cannot be picked until a class is chosen. This prevents admins from selecting a class or fees group that has no `FeesStructure` configured for the target year — which would otherwise cause `assignStudentFeesFromStructure()` to silently return null and admit the student with no billing record.

### Classes — depends on `form.academicYear`

When `form.academicYear` changes, the form calls:

```ts
GET /api/school/classes?academicYear=<year>
```

The endpoint restricts the result set to classes that have at least one active `FeesStructure` for that academic year:

```ts
feesStructures: {
  some: { academicYear, isActive: true, status: 'active', deletedAt: null }
}
```

If the previously selected class is not present in the new list, `classId`, `sectionId`, and `feesGroupId` are all cleared automatically.

### Fees Groups — depends on `form.classId` and `form.academicYear`

When either changes, the form calls:

```ts
GET /api/school/fees/groups?academicYear=<year>&classId=<id>
```

The endpoint restricts the result set to groups that have an active `FeesStructure` for that exact `(classId, academicYear)` pair:

```ts
structures: {
  some: { classId, academicYear, isActive: true, status: 'active', deletedAt: null }
}
```

If the previously selected group is not in the new list, `feesGroupId` is cleared automatically.

### Transport Routes — depends on `form.academicYear`

Transport routes follow the same reactive pattern, fetched whenever `form.academicYear` changes:

```ts
GET /api/school/transport/routes?academicYear=<year>
```

### Why this matters

The same `FeesStructure` lookup is run by `assignStudentFeesFromStructure()` (`src/lib/fees.ts`) at admission submit time. If a class or fees group shows up in the dropdown, the fee assignment is guaranteed to succeed and an invoice + DEBIT ledger entries will be created. If it doesn't show up, the admin cannot pick it — closing the loophole where students could be admitted with zero billing.

### Backward compatibility

Both `/api/school/classes` and `/api/school/fees/groups` accept their filter params as **optional**. When the params are omitted, the endpoints return the unfiltered list — so existing callers (classes admin page, fees admin pages, etc.) continue to work unchanged.

### Empty-state UI

The Class and Fees Group dropdowns show context-aware placeholders ("Select academic year first", "No classes configured for this year", "Select class first", "No fee groups for this class & year") and amber helper text when their lists are empty, prompting the admin to set up the missing `FeesStructure` in **Fees → Structures** before continuing.

## 4. Admission Number Preview

The next admission number is generated by:

`src/app/api/school/admissions/next-number/route.ts`

The route:

- requires an authenticated school user
- checks `admission:read` permission for non-super-admin users
- reads `AdmissionSetting` if available
- falls back to `STD-{YEAR}-{SEQ}`
- checks both `Admission` and `Student` tables to avoid duplicates

Example output:

```json
{
  "nextAdmissionNumber": "STD-2026-001"
}
```

## 5. Frontend Validation

Before moving between wizard steps, the form validates relevant fields.

Main validation helpers:

```ts
validateField()
validateStepFields()
handleNext()
handleSubmit()
```

Examples of frontend validation:

- first name required
- last name required
- date of birth required
- gender required
- father name required
- father phone required
- class required
- Aadhaar format checked if entered
- IFSC and bank account checked if entered
- declaration checkbox required before final submission

## 6. Submission Payload

Before submission, `buildPayload()` converts form state into API payload.

It normalizes values such as:

```ts
aadhaarNumber -> digits only
heightCm -> number
weightKg -> number
motherIncome -> number
fatherIncome -> number
siblingId -> null if empty
```

Then the frontend submits:

```ts
api.post('/api/school/admissions', payload)
```

## 7. Backend Create Route

The create admission API is:

`src/app/api/school/admissions/route.ts`

The `POST` handler:

1. Requires role `SUPER_ADMIN` or `SCHOOL_ADMIN`.
2. Requires `schoolId`.
3. Checks `admission:create` permission for non-super-admin users.
4. Validates request body again on the server.
5. Validates class and section existence.
6. Checks admission window from `AdmissionSetting`, if configured.
7. Checks max applications per class, if configured.
8. Generates a unique admission number.
9. Creates related records inside a Prisma transaction.

Backend validation is important because frontend validation can be bypassed.

## 8. Database Transaction

Admission creation uses:

```ts
db.$transaction(async (tx) => {
  ...
})
```

This means all related records are created together. If any step fails, the database changes are rolled back.

Inside the transaction, the system creates:

1. `Admission`
2. `Student`
3. link from `Admission` to `Student`
4. `Parent` records
5. `StudentParent` relation records
6. parent `User` account, if phone number exists
7. `UserRole` assignment for the parent user
8. `AdmissionActivity` audit records

## 9. Admission Record

The first saved record is `Admission`.

The model is defined in:

`prisma/schema.prisma`

It stores full admission form data, including:

- personal details
- contact and address details
- father and mother details
- class and section
- previous school details
- transport details
- hostel details
- bank/account details
- sibling reference
- workflow status

Current behavior creates the admission directly with:

```ts
status: 'admitted'
```

So this module is currently a direct admission flow, not a pending application approval flow.

## 10. Student Record

After creating the admission, the API creates a `Student` record from the same admission data.

Stored student fields include:

- school ID
- admission number
- first name
- last name
- date of birth
- gender
- class ID
- section ID
- address
- profile image
- previous school details
- sibling ID
- admission status

Then the admission is updated with:

```ts
studentId: student.id
```

This links the `Admission` record to the created `Student`.

## 11. Parent Records

The API creates parent records based on available data:

- father parent record if father name exists
- mother parent record if mother name exists
- guardian parent record if guardian name exists
- fallback basic parent record if none exists

Then it links each parent to the student through `StudentParent`.

The relationship is:

```txt
Student -> StudentParent -> Parent
```

## 11a. Family Grouping (`familyId`)

Sibling relationships are represented by a **shared `familyId`** on every member of the family. Both `Student.familyId` and `Admission.familyId` are populated on admission submit:

- If the admin selected a sibling at admission time (`body.siblingId` is present), the new student adopts the sibling's `familyId`. If the sibling has none (pre-backfill data), one is minted and written back to the sibling's row inside the same Prisma transaction before the new student is created.
- If no sibling is selected, a fresh `familyId` is minted — a "family of one." This makes future linking trivial: any second child admitted later will adopt this id when the admin picks the first child as their sibling.

Reading siblings is then a single query:

```ts
db.student.findMany({
  where: { familyId: student.familyId, id: { not: student.id }, deletedAt: null }
})
```

The legacy `Student.siblingId` / `Admission.siblingId` fields are kept as a breadcrumb (they record which sibling the admin picked at admission time) but no longer drive the read path. The "Siblings" tab on the student detail page renders every family member, regardless of which admission was created first.

A one-time backfill (`scripts/backfill-family-id.ts`) walks every existing `Student.siblingId` chain via union-find and assigns each connected component a shared `familyId`. The script is idempotent.

## 12. Parent Login User

The system creates or reuses a parent login account.

It uses:

1. father phone
2. mother phone
3. guardian phone

The generated parent login looks like:

```txt
email: 9876543210@parent.local
phone: 9876543210
password: parent123
role: PARENT
```

If a user with the same phone already exists, it reuses that user and ensures the parent role is assigned.

## 13. Activity Logs

The transaction creates admission activity records:

```ts
action: 'created'
action: 'admitted'
```

These are stored in `AdmissionActivity` and act as an audit trail.

## 14. Frontend Success State

After a successful API response, the frontend shows a success dialog with:

- student name
- assigned admission number
- parent login credentials, if a parent phone exists

The user can then:

- admit another student
- go to the student list

## 16. Related API Routes

Main admission routes:

```txt
GET  /api/school/admissions
POST /api/school/admissions
GET  /api/school/admissions/[id]
PUT  /api/school/admissions/[id]
DELETE /api/school/admissions/[id]
GET  /api/school/admissions/next-number
GET  /api/school/admissions/stats
GET  /api/school/admissions/[id]/documents
POST /api/school/admissions/[id]/documents
```

Supporting routes used by the form:

```txt
GET /api/school/sections
GET /api/school/academic-years
GET /api/school/classes?academicYear=<year>
GET /api/school/fees/groups?academicYear=<year>&classId=<id>
GET /api/school/transport/routes?academicYear=<year>
GET /api/school/students
GET /api/school/students/[id]/parent-details
GET /api/school/parents/lookup
```

The `academicYear` and `classId` query params on `/api/school/classes` and `/api/school/fees/groups` are optional. When provided, the endpoints filter results to only those tied to an active `FeesStructure` for that scope; when omitted, the full unfiltered list is returned (used by the admin pages for classes and fees groups).

## 17. Documents Limitation

The frontend has a document upload step, but the current upload behavior is simulated.

`handleDocumentUpload()` only updates local React state:

```ts
setDocumentUploads(...)
```

The backend has a real document API:

```txt
POST /api/school/admissions/[id]/documents
```

But the current admission form does not call that route after admission creation. Therefore, document metadata from the wizard is not persisted during the main admission submit flow.

## 18. Overall Flow Summary

```txt
Sidebar click
  -> currentPage = admission-form
  -> AdmissionFormPage loads
  -> fetch sections, academic years, next admission number (initial, year-independent)
  -> user selects academic year
       -> fetch classes for that year (filtered by FeesStructure existence)
       -> fetch transport routes for that year
  -> user selects class
       -> fetch fees groups for (class, year) (filtered by FeesStructure existence)
  -> user fills 6-step wizard
  -> frontend validates
  -> POST /api/school/admissions
  -> backend validates again
  -> generate admission number
  -> Prisma transaction:
       resolve familyId
         if body.siblingId: adopt sibling.familyId (mint + backfill if missing)
         else: mint a fresh familyId (family of one)
       create Admission (with familyId)
       create Student (with familyId)
       link Admission to Student
       create StudentAcademicEnrollment
       create Parent records
       create StudentParent links
       create or reuse Parent User
       assign Parent role
       create AdmissionActivity logs
       assignStudentFeesFromStructure() ->
         lookup FeesStructure(classId, academicYear, feesGroupId)
         create StudentFeeAssignment + items (frozen snapshot)
         create StudentFeeInvoice + lines
         create DEBIT StudentFeeLedgerEntry per item
  -> return admission
  -> frontend shows success dialog
```

Because the Class and Fees Group dropdowns are pre-filtered by the same `FeesStructure` existence rule that drives `assignStudentFeesFromStructure()`, the final fee-assignment step inside the transaction is guaranteed to succeed for any combination the admin could have selected.

## 19. Production Improvement Notes

Recommended improvements:

- Persist uploaded documents after admission creation.
- Wire `AdmissionsPage` into navigation if the school needs a dedicated admissions list.
- Add a real workflow if admissions should move through `applied -> verified -> fee_pending -> admitted`.
- Use per-parent deduplication more consistently instead of always creating new `Parent` records.
- Move admission number generation into a shared server utility to avoid duplication between routes.
- Consider real file upload storage for document files instead of simulated upload state.
